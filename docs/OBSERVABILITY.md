# Observability: durable production logging and request audit

Two complementary layers record every request without ever storing a secret,
a body, a query string, or the claim text. Both survive container recreation,
which is why the V38 and V39 visits on 2026-08-10 could not be traced: the old
nginx logs lived only inside the container and were lost when it was recreated.
This is the fix, so the next external visit is fully recorded.

## The two layers

1. **nginx JSON access log** (`deploy/nginx/conf.d/00-logging.conf`), one line
   per request, written to `/var/log/verifi/nginx/access.json.log` on the host
   through a bind mount, so it outlives the nginx container. Fields: UTC time,
   `request_id`, the direct TCP peer (`remote_addr`), the trusted-corrected
   client (`real_client`), the raw untrusted `xff`, whether the peer was a
   trusted proxy, host, method, path (`$uri`, never the query), status, bytes
   in and out, request and upstream time, upstream address and status, TLS
   version, user agent, referer.

2. **`request_audit` table** in PostgreSQL, one row per money- or human-facing
   request (`rest` /verify and /verify-unlock, `mcp` tool calls, `website`
   contact form). It survives everything the container layer cannot, and is
   the durable record for investigating a visit.

The two layers and the `verifies` row share one **`request_id`**, generated by
nginx, returned to the caller in the `X-Request-ID` header, and stored on both
the audit row and, for a created verification, the verify row.

## Trust boundary

nginx is the edge. A client connects directly (its TCP peer is its real public
address) or through a trusted proxy (loopback, the docker network, or Tailscale
CGNAT `100.64.0.0/10`). `X-Forwarded-For` is believed only when the peer is one
of those proxies (`set_real_ip_from` + `geo $fwd_trusted`). A public caller's
peer is public, never in the trusted set, so it can never forge a trusted
client IP. The audit stores `client_ip` (the trusted address), `forwarded_for`
(the raw header, untrusted), and `forwarded_trusted` (the flag), separately.

`X-Verifi-Source` is forced to `rest` by nginx on the public `/verify`, so only
the internal MCP server can label a request `mcp`. Identity is never inferred
from a bare `agent_id`: the free-form wallet string is not proof. Only a
verified x402 signature sets `wallet_ownership_proven = true`.

## What is never logged

Authorization, PAYMENT-SIGNATURE, PAYMENT-RESPONSE, cookies, private keys,
`.env` contents, x402 signatures, Telegram tokens, DB passwords, full callback
URLs (host only), intent or claim text, and any request or response body. The
claim is reduced to `claim_len` and `claim_sha256`; the real claim stays in the
`verifies` table. `tests/test_logging_redaction.py` locks these rules down.

## Retention, rotation, permissions, privacy

IP addresses are personal data. The host logs rotate daily, keep **30 days**,
are compressed, and are created `0640 root:adm`, so only root and the `adm`
group can read them (`deploy/logrotate/verifi-nginx`). After rotation nginx is
told to reopen its files. The `request_audit` table holds `client_ip` and
should be pruned on the same 30 day horizon by the operator; a scheduled
`DELETE FROM request_audit WHERE at < now() - interval '30 days'` satisfies
this. Review whether the privacy policy needs to mention IP retention.

## Setup and deploy

`verifi deploy` (including the automatic deploy on push to `main`) creates the
host log directory, installs the logrotate config, and validates the nginx
config in a throwaway container **before** recreating anything, so a broken
edge config aborts the deploy instead of crashing the public surface.
`verifi logging-setup` does the same on demand. `verifi acceptance-logging`
runs the production acceptance suite (`scripts/acceptance-logging.sh`).

## Investigating a visit

All of these read from the durable audit table, so they work after any
container recreation. Run on the server:

```sh
J="docker exec verifi-postgres-1 psql -U verifi -d verifi"
```

By **verify number** (the Telegram-visible `#V-<n>`):

```sh
$J -c "SELECT at, source, route, client_ip, forwarded_for, forwarded_trusted,
              user_agent, agent_id, request_id, http_status, payment_required,
              admission_source, funding_state, outcome, wallet_ownership_proven
       FROM request_audit WHERE verify_no = 38;"
```

By **time window** (e.g. the V38 and V39 morning):

```sh
$J -c "SELECT at, source, route, client_ip, agent_id, verify_no, request_id,
              http_status, outcome, wallet_ownership_proven
       FROM request_audit
       WHERE at BETWEEN '2026-08-10T06:56:00Z' AND '2026-08-10T06:57:30Z'
       ORDER BY at;"
```

By **claimed agent_id** (remember: a match is only a claim, not proof, unless
`wallet_ownership_proven` is true):

```sh
$J -c "SELECT at, source, verify_no, client_ip, request_id, outcome,
              wallet_ownership_proven
       FROM request_audit WHERE lower(agent_id) = lower('0x...') ORDER BY at DESC;"
```

By **request_id** (ties the audit row to the nginx log line and the verify
row):

```sh
$J -c "SELECT a.at, a.source, a.route, a.client_ip, a.outcome,
              v.verify_no, v.status
       FROM request_audit a
       LEFT JOIN verifies v ON v.request_id = a.request_id
       WHERE a.request_id = '<request_id>';"

# and the matching nginx access log line(s):
grep '"request_id":"<request_id>"' /var/log/verifi/nginx/access.json.log
```

The nginx log holds the network view (bytes, timing, TLS, user agent); the
audit table holds the application view (funding, outcome, proof of ownership).
Join them on `request_id`.

## Production acceptance result (2026-08-11)

Run on the server via `verifi acceptance-logging` (Server ops run 31510647278),
against the live `https://verifi.cloud`. It spent no money and created no human
work: the REST and MCP probes were unpaid and stopped at the 402 gate. All ten
checks passed.

```
PASS: REST response carried X-Request-ID
PASS: MCP response carried X-Request-ID
PASS: REST request_id is in the nginx JSON access log
PASS: REST audit row exists with source=rest
PASS: rest and mcp rows both present in the last 2 minutes (rest and mcp distinguishable)
PASS: forged X-Forwarded-For was recorded as untrusted
PASS: access log contains no secret, claim, or intent tokens
PASS: access log persisted across nginx recreate (28 lines before, 28 after)
PASS: logrotate config parses
PASS: log dir permissions are 750
== Acceptance done: 10 passed, 0 failed ==
```

This confirms the finish line: logs survive container recreation, REST and MCP
are distinguishable, requests correlate to their audit rows by request_id, no
secret is logged, and a forged forwarded header is not trusted. Re-run any time
with `verifi acceptance-logging`.
